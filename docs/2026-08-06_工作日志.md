### 1. 管理员 API Key 认证 ✅

**问题**：`/api/v1/admin/*` 下 6 个端点（数据采集、模型训练、系统状态、手动录入等）完全公开，任何人可触发。

**方案**：Simple API Key via `X-API-Key` Header。选型理由：

- 空 Key = 跳过认证，向后兼容开发环境

**实现**：

| 层 | 文件 | 改动 |
|---|---|---|
| 配置 | `backend/app/config.py` | 新增 `admin_api_key: str = ""` |
| 认证依赖 | `backend/app/api/admin.py` | `require_admin()` 函数 + `APIRouter(dependencies=[...])` 路由级应用 |
| 环境变量 | `.env` + `docker-compose.yml` | `ADMIN_API_KEY=nba-predictor-admin-2024` |
| 前端拦截器 | `frontend/src/api/client.ts` | `request` 拦截器从 localStorage 读取并注入 `X-API-Key` header |
| 前端 UI | `frontend/src/pages/AdminPage.tsx` | 密钥输入框、localStorage 持久化、状态指示器 |

**原理**：FastAPI 的 `Depends()` 依赖注入系统允许在路由层面添加"守卫"。`APIRouter(dependencies=[Depends(require_admin)])` 使得该路由器下的**所有**端点自动执行 `require_admin` 函数，无需逐个端点添加装饰器。

实际执行时：
1. 请求到达 → FastAPI 解析 `X-API-Key` header
2. `require_admin()` 被调用 → 比较 `settings.admin_api_key` 与 header 值
3. 匹配 → 请求继续；不匹配 → 抛出 `HTTPException(401)`
4. `admin_api_key` 为空字符串时直接放行（开发模式）

**验证结果**：
```bash
无 Key      → HTTP 401 ✅
错误 Key    → HTTP 401 ✅
正确 Key    → HTTP 200 ✅
```

### 2. 数据库性能索引 ✅

**问题**：`build_training_dataset()` 对 30,777 场比赛逐条查询，`games`、`team_game_stats`、`game_player_stats` 三张表无查询优化索引，全表扫描导致训练超时，之前只能用 8 赛季 4,155 样本。

**方案**：在 PostgreSQL 中直接创建 11 个索引（项目未配置 Alembic 迁移框架）。

**创建的索引**：
```sql
-- games 表（最核心的查询表）
CREATE INDEX idx_games_game_date ON games(game_date);       -- 按日期过滤
CREATE INDEX idx_games_home_team ON games(home_team_id);    -- 按主队查询
CREATE INDEX idx_games_away_team ON games(away_team_id);    -- 按客队查询
CREATE INDEX idx_games_status    ON games(status);           -- 按状态过滤(Final/Scheduled)
CREATE INDEX idx_games_season    ON games(season);           -- 按赛季过滤

-- team_game_stats 表
CREATE INDEX idx_team_game_stats_game ON team_game_stats(game_id);   -- JOIN games
CREATE INDEX idx_team_game_stats_team ON team_game_stats(team_id);   -- 按球队聚合

-- game_player_stats 表
CREATE INDEX idx_game_player_stats_game   ON game_player_stats(game_id);    -- JOIN games
CREATE INDEX idx_game_player_stats_player ON game_player_stats(player_id);  -- 按球员聚合

-- 复合索引（覆盖最常见的特征查询模式）
CREATE INDEX idx_games_home_date ON games(home_team_id, game_date);
CREATE INDEX idx_games_away_date ON games(away_team_id, game_date);
```

**原理**：B-tree 索引将查询复杂度从 O(n) 全表扫描降为 O(log n)。对于 `WHERE home_team_id = X AND game_date < Y ORDER BY game_date DESC` 这类查询，复合索引 `(home_team_id, game_date)` 可以一次索引查找完成过滤+排序，无需额外排序步骤。

`EXPLAIN` 验证（以 TeamFeatures 最常用的查询为例）：
```sql
-- 无索引: Seq Scan on games (rows=30777) → 扫描全表
-- 有索引: Index Scan using idx_games_home_date (rows=~82 per team) → 仅扫描相关行
```

### 3. 特征工程 — 对手调整统计 ✅

**问题**：当前 `TeamFeatures` 只统计球队原始数据（场均得分、篮板等），不考虑对手强弱。一支场均 120 分的球队如果一直打防守垫底的球队，其进攻实力被高估。

**方案**：新建 `ml/src/features/opponent_adjusted_features.py`，对球队最近 N 场比赛中的每一场，计算对手的赛季平均防守/进攻水平，将球队表现除以对手平均水平得到调整后的比率。

**6 个新特征**：

| 特征名 | 含义 | 计算方式 |
|--------|------|---------|
| `opp_adj_pts` | 对手调整得分 | 球队实际得分 / 对手场均失分 |
| `opp_adj_pts_allowed` | 对手调整失分 | 球队实际失分 / 对手场均得分 |
| `opp_adj_net_rtg` | 对手调整净效率 | 本场净胜分 - 对手赛季平均净胜分 |
| `opp_adj_off_rtg` | 对手调整进攻效率 | 球队得分 / 对手场均防守效率 |
| `opp_adj_def_rtg` | 对手调整防守效率 | 球队失分 / 对手场均进攻效率 |
| `sos_rating` | 赛程强度 | 所有对手的平均胜率 |

**原理**：这是篮球分析中 SRS（Simple Rating System）思路的简化版。SRS = 场均净胜分 + 对手平均净胜分。核心洞察：
- 球队 A 赢弱队 20 分的含金量 < 球队 B 赢强队 5 分
- 通过对手质量加权，还原球队的"真实实力"
- 例如：`opp_adj_pts = 1.10` 表示该队面对对手时得分比对手通常失分高 10%，说明进攻强于对手防守水平

**实现要点**：
- 对球队最近 10 场比赛，逐场查询对手在该场比赛前的赛季平均数据
- 使用 `game_date < before_date` 确保无数据泄露（只用比赛前的信息）
- 对手数据不足时返回默认值（neutral baseline）

**⚠️ 性能注意事项**：此模块在 `build_training_dataset()` 中会对每场比赛发起额外的对手统计查询。对于 30,777 场比赛 × 2 队 = ~60K 次额外查询。这解释了为什么全量训练比之前更慢。**优化方向**：在 `build_training_dataset` 中预计算所有球队的赛季统计数据，避免逐场重复查询。

### 4. 特征工程 — 旅行/体力因素 ✅

**问题**：NBA 球队频繁长途飞行，背靠背比赛对体能影响显著。现有特征只有简单的 `home_b2b`/`away_b2b` 和 `rest_days`，未量化旅行距离和连续客场效应。

**方案**：扩展 `ml/src/features/context_features.py`。

**4 个新特征**：

| 特征名 | 含义 | 计算方式 |
|--------|------|---------|
| `travel_distance_category` | 旅行距离等级 | 0=同城(LAL vs LAC), 1=<500mi, 2=500-1500mi, 3=>1500mi(跨岸) |
| `home_travel_fatigue` | 主队旅途疲劳 | 主队是否刚结束客场之旅（前 N 场连续客场的次数） |
| `away_travel_fatigue` | 客队旅途疲劳 | 客队连续客场场次 |
| `home_days_since_home` | 主队离家天数 | 主队上次在主场比赛距今多少天 |

**原理**：
- **旅行距离**：NBA 研究中，跨岸飞行（>1500mi）对客场球队胜率影响约 -5% 到 -8%。使用 Haversine 公式计算球面距离：`d = 2 × R × arcsin(√(sin²(Δlat/2) + cos(lat₁)cos(lat₂)sin²(Δlon/2)))`
- **连续客场**：连续的客场不仅代表旅行疲劳，还代表缺乏训练时间和睡眠不足。通常第 3 场连续客场的负效应最大
- **主场间隔**：长时间未在主场比赛意味着球队处于长客场之旅中，对体能和精神状态都有影响

**球队坐标**：硬编码了 30 支 NBA 球队球馆的经纬度，`NBA_ARENA_COORDS` 字典。

## 四、优化建议（供参考）

### opponent_adjusted_features 性能优化

当前瓶颈在于 `_get_opponent_season_stats()` 在训练循环中逐场查询。优化方案：

**方案 A：批量预计算（推荐）**
在 `build_training_dataset()` 开始前，一次性查询所有球队在每个赛季的统计数据，存入 `dict[(team_id, season)] -> stats`。后续 `compute()` 直接从内存读取。
```python
# 伪代码
opponent_cache = {}
for team_id in all_teams:
    for season in seasons:
        opponent_cache[(team_id, season)] = compute_season_stats(team_id, season)
```

**方案 B：SQL 窗口函数**
用单个 SQL 查询计算每个球队在每个时间点的滚动平均，避免 Python 循环中的 N+1 查询问题。

**方案 C：减少对手统计查询精度**
不查每场比赛对手的"截至当时"统计，而是用对手整个赛季的平均值（轻微数据泄露，但对预测影响极小）。

## 五、学习参考：今日优化原理

### 为什么特征工程比超参调优更重要？

上次 Optuna 调优（30 trials）只改善了 ~1%（Combined MAE 13.89→13.75）。原因：

1. **XGBoost 的超参空间相对平坦**：在合理范围内，max_depth 3-6、lr 0.03-0.10 的效果差异不大
2. **信息瓶颈在输入特征，不在模型容量**：模型已经学到了数据中可学的模式，剩余误差来自缺失的信息维度
3. **类比**：给一个顶级厨师（好模型）提供有限的食材（差特征），他只能做出一定水平的菜。超参调优相当于微调火候——有帮助但有限。特征工程相当于增加新食材——质变而非量变。

### 为什么对手调整统计重要？

考虑两个场景：
- **球队 A**：场均 115 分，但面对的对手防守效率排名都在倒数 5 名
- **球队 B**：场均 108 分，但面对的是联盟前 5 防守

原始特征会认为 A 更强，但 `opp_adj_pts` 会揭示真相——A 的得分被对手弱防守"注水"了。

这正是 NBA 博彩中"fade the public"策略的量化基础——普通球迷只看原始数据，价值在对数据做对手调整。

### 为什么旅行距离影响比赛结果？

NBA 赛程极其密集（82 场/6 个月），研究表明：
- 背靠背第二场客队胜率下降约 6-8%
- 连续第 3+ 场客场的球队 ATS（Against The Spread）表现显著下降
- 从西岸飞东岸的球队（失去 3 小时），表现低于预期

机器学习模型如果不能量化这些因素，会让分预测出现系统性偏差。
