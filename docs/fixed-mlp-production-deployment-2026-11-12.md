## 旧协议隔离与调度

四个观察器保持原镜像、原协议、原记录。旧选择器与模型元数据冻结到独立只读卷 `nba-frozen-1022-models-v2`，观察器根目录 `/frozen_models`；实际模型文件放在该卷内，满足原包路径及文件哈希校验。观察记录仍写原记录目录，未复制成另一份成绩。

旧总分自动采集从主 API 调度器拆分到 `nba-total-observer`，使用原冻结服务代码，只执行原 `capture_due` 循环。主 API 关闭本地旧总分捕获任务，经内部 HTTP 转接该观察器状态；数据采集、名单同步、正式协议检查和夜间赛果结算调度保留。夜间任务仍为 evaluate-only，不自动训练或晋升。

部署后核对：总分留档 10、结算 10，协议匹配；胜负留档／结算 7；旧配对留档／结算 5；修复安全队列仍为 0。完整性错误均为 0。旧配对中的旧 MLP 异常不能当成已上线修复版的表现；修复观察器状态里的 `production_promoted:false` 声明该观察器自身不执行晋升，不代表主 API 的当前版本。

原始文件级 active 挂载方案在当前 Docker 环境中未能隔离共享目录的原子替换，切换后旧协议临时不匹配、状态返回 503。已改为真正独立的模型／清单副本卷并重新验证。期间协议按设计拒绝新增不匹配记录，没有改写旧协议来掩盖问题。最终主 API 转接与四个观察器均已恢复正常。

部署核验脚本曾把单样本 XGBoostPrediction 对象当成列表，报错时两条真实预测已经保存；随后仅重放这些既有记录，并使用 `persist=false` 核对新响应，没有重复创建预测。

最后核验前端代理时发现旧 Nginx 缓存了后端重建前的 IP，网页 API 返回 502；已先重载恢复，再将动态 Docker DNS 配置固化为新镜像。已将网页代理路径列入最终验收，不能只凭后端 `/health` 判断整站可用。

## 启停与回滚

统一生产入口：

```powershell
./scripts/production_stack.ps1 ps
./scripts/production_stack.ps1 up
```

该入口使用六份配置：基础、release、injury-chain、paired-models、win-shadow、fixed-mlp。不要省略 fixed-mlp 覆盖，它包含冻结卷与独立观察器编排。`up` 不训练、不重新构建或再次激活选择器。独立卷是现有外部卷，迁移到其他电脑时必须一并备份恢复或按冻结包重新初始化。

本轮还更新了 release 配置的主 API 镜像和转接环境，避免常用 release 命令退回不认识修复合同的旧代码。

首选行为回滚（已在隔离环境验收，不在生产反复演练）：

```powershell
docker exec nba-backend python /app/scripts/fixed_mlp_release.py rollback --models-dir /app/ml/saved_models --package /app/ml/saved_models/repair_releases/mlp_input_repair_20261112_release_v1
docker restart nba-backend
```

保留兼容代码并恢复旧选择器即可回到旧 MLP 行为，四个独立观察器不受该切换影响。数据库保留 010，不缩短版本字段、不删除新预测。需要再回退代码镜像时，应先完成选择器回滚，并处理原调度器可能重复捕获旧总分的问题；不要直接换回旧镜像。

修复包不可变目录保留 `baseline.json`、`candidate.json`、证据及模型文件哈希。兼容镜像保留，用于回滚后重放修复期间的记录。
