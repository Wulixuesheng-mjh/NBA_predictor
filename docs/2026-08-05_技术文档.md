## 1. Docker VHDX 磁盘空间回收与数据迁移

### 1.1 问题背景

Docker Desktop on Windows 使用 WSL2 后端，所有 Docker 数据（镜像、容器、卷）存储在 VHDX 虚拟磁盘文件中：

```
C:\Users\<用户>\AppData\Local\Docker\wsl\disk\docker_data.vhdx
```

**VHDX 的核心特性**：
- **动态扩展**：创建时很小，按需增长
- **永不自动收缩**：即使内部删除数据，VHDX 文件大小不变

### 1.2 为什么压缩 VHDX 极其困难

尝试了以下 5 种方案，全部失败或效果甚微：

| 方案 | 原理 | 失败原因 |
|---|---|---|
| `diskpart compact vdisk` | 回收 VHDX 尾部连续空闲空间 | 内部碎片化，尾部无连续空闲 |
| `Optimize-VHD` | Hyper-V 工具 | 系统未安装 Hyper-V 模块 |
| `convertvhd.exe` | VHD↔VHDX 互转 | 不支持 VHDX→VHDX 同格式转换 |
| WSL `fstrim` + `diskpart` | 先发送 TRIM 再压缩 | TRIM 命令被 WSL 层拦截，无法传播到 NTFS 上的 VHDX |
| 导出 WSL 发行版 | `wsl --export` 重建 | 本机仅有 `docker-desktop`（无 `docker-desktop-data` 独立发行版） |

**核心障碍：TRIM 无法穿透 WSL 层**

```
应用层:    fstrim /mnt → 发送 DISCARD ioctl
              ↓
ext4:      标记块为空闲
              ↓
WSL2 内核: 接收 DISCARD，转换为 SCSI UNMAP
              ↓
Hyper-V:   接收 UNMAP，应通知 VHDX 文件系统
              ↓
NTFS:      ❌ UNMAP 在此丢失 —— NTFS 上的 VHDX 不支持 hole punching
```

当 VHDX 文件存储在 NTFS 上时，Windows 的虚拟磁盘驱动不会将 UNMAP 命令转换为 NTFS 稀疏文件操作。这是 WSL2 架构的已知限制。

### 1.3 解决方案：跨盘迁移 + 目录联结

既然无法压缩 VHDX，改用空间换空间策略：

```
C:\Users\...\AppData\Local\Docker  →  E:\DockerData
                                   ↑
                           mklink /J (Junction)
```

**技术要点**：

1. **robocopy**：Windows 原生工具，支持大文件续传和权限保留
2. **NTFS Junction (`mklink /J`)**：目录级别的符号链接，对应用程序透明
   - 与 `mklink /D`（符号链接）不同，Junction 只支持绝对路径且只能指向本地卷
   - Docker Desktop 通过原路径访问时完全感知不到数据已迁移
3. **权限修复**：跨盘 Junction 可能丢失 NTFS ACL，需手动 `icacls` 授权

### 1.4 后续建议

- 定期监控 VHDX 大小：`Get-Item docker_data.vhdx | Select Length`
- 当 VHDX 再次膨胀时，考虑"核选项"：导出 PostgreSQL 数据 → 删除 VHDX → 重建 → 恢复数据
- 长期方案：使用独立的 Linux 分区或迁移到纯 Linux 环境

## 2. NBA 数据采集从 nba_api 到 Kaggle 的切换

### 2.1 问题根因

`nba_api` 库（v1.11.4，2026-02-20 发布）依赖 `stats.nba.com` 的 REST API。从 2026 年中起，NBA 强化了 Cloudflare 防护：

```
HTTP GET https://stats.nba.com/stats/leaguegamefinder?Season=2025-26
     ↓
Cloudflare 检测请求非来自真实浏览器
     ↓
返回 HTTP 200 + NBA.com 首页 HTML（而非 JSON）
     ↓
nba_api → json.loads() → JSONDecodeError
```

**关键发现**：
- 即使设置完整的浏览器模拟请求头（User-Agent、Referer、Origin、x-nba-stats-token 等），API 仍返回 HTML
- 这表明 Cloudflare 使用了 JS Challenge 或更高级的指纹检测
- 这是 NBA 官方主动封锁第三方 API 访问的举措

### 2.2 替代方案

项目已有 `kagglehub` 依赖（在 `ml/Dockerfile` 中），直接使用 Kaggle 数据集作为数据源。

**选择 `nathanlauga/nba-games` 的原因**：
- CSV 格式，无需额外解析
- 包含完整的比赛结果（`games.csv`）+ 球员数据（`games_details.csv`）
- 文件大小适中（21MB 压缩包）
- 列结构与项目 ORM 模型高度兼容

### 2.3 数据导入流程

```
Kaggle 数据集 (CSV)
     ↓
teams.csv → teams 表 (NBA ID → 内部 ID 映射)
     ↓
players.csv → players 表
     ↓
games.csv → games 表 + team_game_stats 表
     ↓
games_details.csv → game_player_stats 表
```

**关键技术决策**：

1. **幂等导入**：使用 PostgreSQL `INSERT ... ON CONFLICT DO UPDATE` 支持重复执行
2. **批量提交**：每 500-1000 行提交一次，平衡内存与性能
3. **数据类型适配**：
   - `minutes` 字段：Kaggle 为 `MM:SS` 格式，数据库为 `VARCHAR(10)`，需截断异常长值
   - `season` 字段：Kaggle 用单个年份（如 `2022`），与系统预期的 `2024-25` 格式不同，但数据库层面兼容

### 2.4 局限性

- 数据仅到 2022 赛季（2022-23 NBA 赛季）
- 缺少 2023-2026 赛季数据
- 球员信息为历史数据，不反映当前阵容

## 3. Nginx 反向代理 307 重定向修复

### 3.1 问题现象

前端页面无法加载球队列表和生成预测，浏览器控制台显示 API 请求失败。

### 3.2 根因分析

**请求链路**：

```
浏览器 → Nginx(:3000) → FastAPI(:8000)
```

**问题触发**：

```
1. 浏览器: GET /api/v1/teams
2. Nginx: proxy_pass → backend:8000/api/v1/teams
3. FastAPI: 路由定义为 /teams/（有尾斜杠）
           返回 307 Location: http://localhost/api/v1/teams/
                                   ↑ 缺少端口号 :3000
4. 浏览器: 跟随重定向到 localhost:80 → 连接失败
```

**根因是两层问题**：

1. **FastAPI/Starlette** 的 trailing slash redirect 机制：当请求 `/teams` 而路由定义为 `/teams/` 时，自动返回 307
2. **Nginx** 的 `proxy_set_header Host $host;` 只传递了 `localhost`，未包含端口 `:3000`。Starlette 根据 `Host` 头构造重定向 URL

### 3.3 解决方案

**方案 A**（当前采用）：Nginx `proxy_redirect` 重写

```nginx
proxy_redirect http://localhost/ http://$host:3000/;
```

将后端返回的 `Location: http://localhost/...` 重写为 `Location: http://localhost:3000/...`

**方案 B**（备选）：Nginx 传递完整 Host

```nginx
proxy_set_header Host $host:$server_port;
```

**方案 C**（更彻底）：前端统一使用尾斜杠

```typescript
apiClient.get("/teams/")  // 而非 /teams
```

### 3.4 架构启示

在 Docker Compose 多容器架构中，每个服务监听不同端口，反向代理必须正确处理：
- **Host 头传递**：包含端口号
- **X-Forwarded-*** 头：让后端感知原始请求信息
- **Redirect 重写**：纠正后端生成的重定向 URL

## 4. XGBoost + MLP 双模型训练流程

### 4.1 架构设计

```
                    ┌──────────────────┐
                    │   FeatureBuilder  │
                    │   126 维特征向量   │
                    └────────┬─────────┘
                             │
              ┌──────────────┼──────────────┐
              ▼              ▼              ▼
        XGBoost Win    XGBoost Spread  XGBoost Total
        (分类)          (回归)           (回归)
              │              │              │
              └──────────────┼──────────────┘
                             │
                    ┌────────▼─────────┐
                    │   Calibration    │
                    │   偏差校正        │
                    └────────┬─────────┘
                             │
                    ┌────────▼─────────┐
                    │   Consensus      │
                    │   双模型一致性     │
                    └────────┬─────────┘
                             │
                    ┌────────▼─────────┐
                    │   Prediction     │
                    │   + SHAP 解释     │
                    └──────────────────┘
```

### 4.2 XGBoost 模型

**三个独立模型**（不共享参数）：
- **Win Model**：`binary:logistic`，预测主队胜率
- **Spread Model**：`reg:squarederror`，预测主队得分 - 客队得分
- **Total Model**：`reg:squarederror`，预测主队得分 + 客队得分

**为什么分为三个模型**：让分和总分的预测目标不同（一个关注差值，一个关注总和），共享特征但独立学习能获得更好的专业表现。

### 4.3 MLP 模型

**PyTorch 架构**：
```
输入 (126) → Linear(128) → BN → ReLU → Dropout(0.3)
          → Linear(96)  → BN → ReLU → Dropout(0.3)
          → Linear(64)  → BN → ReLU → Dropout(0.3)
          → Linear(32)  → BN → ReLU
          → 3 Heads:
              Win (Sigmoid)
              Spread (Linear)
              Total (Linear)
```

**训练技巧**：
- AdamW 优化器（带权重衰减的 Adam）
- ReduceLROnPlateau 学习率调度
- Early Stopping（patience=50）
- Huber Loss（对离群值更鲁棒）

### 4.4 校准（Calibration）

模型输出的概率可能存在系统性偏差。校准通过简单但有效的加性+乘性校正来修正：

```
calibrated_win_prob = win_prob + win_bias
calibrated_spread  = predicted_spread + spread_bias
calibrated_total   = predicted_total + total_bias
```

偏差系数从最近 30 天的实际比赛结果中计算，当前使用 866 场历史数据进行校准。

### 4.5 当前模型性能与改进方向

| 指标 | 当前值 | 目标值 | 差距 |
|---|---|---|---|
| Win Accuracy | 66.4% | 70%+ | 接近 |
| Spread MAE | 10.60 | < 5.0 | 差距大 |
| Total MAE | 13.45 | < 5.0 | 差距大 |

**改进方向**：
1. **更多训练数据**：当前仅 5,770 样本（5 个赛季），增加到 10+ 赛季
2. **特征工程**：对手调整效率、海拔/旅程距离、裁判倾向
3. **模型集成**：LightGBM + CatBoost + XGBoost 加权平均
4. **场景细分**：为主场龙/客场虫、进攻型/防守型球队训练专用模型
5. **超参调优自动化**：Optuna 搜索结果自动应用到配置
